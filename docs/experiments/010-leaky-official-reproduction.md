# 010. 가이드북 방식 재현 (의도적 데이터 누수 정량화)

> **경고: 이 실험은 CLAUDE.md "필수: 검증 규율"을 의도적으로 위반한다.**
> 아래 "leaky" 조건의 수치는 **불량 예측 성능으로 인용하지 않는다.** 이 실험의 목적은
> "공식 가이드북이 쓰는 행 단위 무작위 분할이 점수를 얼마나 부풀리는지"를 정량화하는
> 것 하나뿐이다. 프로젝트의 정식 결과는 여전히 007(experiment-그룹 분할)이다.

## 날짜
2026-09-07

## 한 일
사용자 질문("데이터 누수를 좀 감당하고 가이드북대로 한번 진행해보는건 어떻게 생각해?")에
대해, 007과 직접 비교하는 대신 **더 통제된 설계**로 진행했다: 같은 row-level 데이터,
같은 feature, 같은 모델·하이퍼파라미터를 고정하고 **분할 방법만** 바꿔서 두 조건을 비교한다.

- `src/features/build_features_v5_leaky_rows.py`: `experiment_XX.csv`의 원본 타임스텝을
  그대로(집계하지 않고) 한 행씩 사용, `train.csv`의 `defect`(=NOT(machining_finalized AND
  passed_visual_inspection)) 라벨을 실험 내 모든 행에 broadcast. 006/007과 동일하게 라벨
  충돌 쌍(No 19/25)은 제외, 총 23개 실험 · 30,918행 · 44개 feature(상수 컬럼 4개 제외,
  `Machining_Process`는 가이드북과 동일한 0~9 순서 인코딩).
  - **leaky** 분할: `train_test_split(shuffle=True, stratify=defect, test_size=0.2,
    random_state=42)`를 전체 행에 대해 실행 — `No`를 전혀 보지 않음(가이드북 방식 그대로).
  - **grouped** 분할: 007의 고정 분할(`TRAIN_NOS`/`TEST_NOS`, 18/5 실험)을 그대로 재사용 —
    한 실험의 모든 행이 항상 같은 쪽에 있음.
- `src/models/train_leaky_official.py`: logreg(C=0.1, balanced) / RF(200그루, depth=3,
  balanced, seed 0~4) — 007과 동일한 고정 하이퍼파라미터를 두 분할에 각각 적용, 단일
  train/test 평가(CV 아님, 가이드북도 CV를 안 씀). 추가로 각 분할에 대해 **그룹 단위 라벨
  순열검정**(실험별로 라벨을 통째로 무작위 재배정, 10회)을 같이 돌려서, 라벨이 완전히
  무의미해져도 leaky 분할에서 점수가 유지되는지 확인했다.
- 신경망(가이드북의 6-hidden-layer Dense MLP)은 재현하지 않았다 — 이 실험의 변수는
  "분할 방법"이지 모델 구조가 아니기 때문(사용자에게 사전에 확인한 스코프).
  스케일러를 train/test 각각 따로 fit하는 가이드북의 관례도 재현하지 않았다(logreg
  파이프라인의 `StandardScaler`를 관례대로 train에서만 fit).

## 결과
(전체 수치는 `reports/metrics.json`의 `"010"` 참고)

| 조건 | 모델 | 실제 라벨 balanced_accuracy | 그룹 순열검정 null 평균 |
|---|---|---|---|
| **leaky** (행 단위 셔플) | logreg | 0.890 | **0.696** |
| **leaky** (행 단위 셔플) | RF | 0.905 | **0.761** |
| **grouped** (실험 단위, 007과 동일) | logreg | 0.683 | 0.410 |
| **grouped** (실험 단위, 007과 동일) | RF | 0.578 | 0.392 |

핵심 발견 — **leaky 조건은 라벨을 완전히 무작위로 섞어도 balanced_accuracy가 0.70~0.76에
머문다.** 무작위 라벨인데 0.5(우연)를 훨씬 웃도는 이유는 라벨 신호가 아니라, 모델이 "이
행의 원본 센서값 패턴이 어느 실험 소속인지"를 기억해뒀다가 그 실험의 (지금은 무의미해진)
라벨을 그대로 답으로 내놓기 때문이다 — 같은 실험의 타임스텝이 train/test 양쪽에 다 있어서
가능한 일이다(23개 실험 전부가 양쪽에 걸쳐 있음을 직접 확인). 반면 grouped 조건의 순열
null은 0.39~0.41로 우연 수준 근처에 머문다(007/009와 일관).

즉 leaky 조건의 "실제 라벨" 점수(0.89~0.91)를 두 부분으로 나누면:
- **행-정체성 암기로 인한 바닥값**: ~0.70~0.76 (null이 이미 여기 있음)
- **라벨이 실제로 더한 부분**: logreg +0.194, RF +0.145 (real - null)

grouped 조건의 "라벨이 실제로 더한 부분"은 logreg +0.273, RF +0.186으로 오히려 leaky보다
크거나 비슷하다 — 즉 **진짜 신호의 크기는 두 조건이 비슷한데, leaky 조건은 여기에 스스로
만든 ~0.35 포인트짜리 암기 바닥값을 얹어서 최종 숫자를 부풀린다.** 공식 가이드북이 보고한
91.51%/99.60%도 정확히 이 메커니즘(행 단위 셔플로 같은 실험의 타임스텝이 학습에 이미
포함된 상태에서 평가)으로 설명 가능하다는 점이 이 실험으로 뒷받침된다.

부가 확인: `experiment_14`/`experiment_24`(바이트 단위로 동일한 텔레메트리, 006/007에서도
발견된 쌍)가 leaky 분할에서 train과 test 양쪽으로 갈라졌다(`duplicate_pair_leaks_across_leaky_split:
true`, 빌드 스크립트 출력) — 행 단위 셔플 자체의 누수 위에 이 중복쌍이 겹쳐 있는 **이중
누수**다. 가이드북 방식은 이런 중복도 전혀 걸러내지 않는다.

## 다음 액션 / 에이전트 지침
- **`leaky` 하위의 어떤 수치도 "성능"으로 인용하지 않는다** — `docs/experiments/`나
  `reports/metrics.json` 밖으로 이 숫자를 옮길 때는 반드시 이 경고를 같이 옮긴다.
- 이 실험은 "가이드북 방식이 우리 프로젝트보다 낫다"는 근거가 아니라 **반대** 근거다:
  같은 데이터·같은 모델에서 분할만 바꿨는데 순열(무의미 라벨) null이 0.39→0.70대로
  뛰었다는 것 자체가, 가이드북 수치의 상당 부분이 라벨과 무관한 구조적 암기라는 직접
  증거다.
- 앞으로 누군가 "가이드북 성능이 더 좋던데 왜 우리는 그렇게 안 하냐"고 물으면 이 문서를
  근거로 답한다.
- 근본 문제(독립 실험 25개라는 표본 크기 한계)는 이 실험으로도 해결되지 않는다 — 다음
  단계는 여전히 더 큰 독립 표본을 가진 데이터셋(PHM 2010 Milling, NASA Milling 등) 확보다.
