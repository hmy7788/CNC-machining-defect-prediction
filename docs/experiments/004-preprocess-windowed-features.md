### (1) 002에서 그대로 물려받은 것 (재결정하지 않음)
003과 깨끗하게 비교하기 위해 아래는 재계산하지 않고 스크립트에 **상수로 못 박았다**.

- 제외 실험: `No` = 14, 19, 24, 25
  (`docs/failures/002-duplicate-experiment-conflicting-labels.md`) → 21건 사용.
- 타겟: `tool_condition_worn` (worn=1 / unworn=0). 보조 타겟
  `passed_visual_inspection_yes`, 라벨성 컬럼 `machining_finalized_yes`도 002와 동일하게 함께 저장.
- **train 실험 16개**: `No` = 1, 2, 3, 5, 6, 7, 9, 10, 11, 13, 17, 18, 20, 21, 22, 23
- **test 실험 5개**: `No` = 4, 8, 12, 15, 16
  → `train_test_split`을 **다시 돌리지 않았다**. 002의 seed=42 결과 목록을 `TRAIN_NOS`/`TEST_NOS`
  리터럴로 복사했고, 스크립트가 매 실행마다
  `assert sorted(TRAIN_NOS + TEST_NOS) == kept_nos`로 이 목록이 실제 보존 실험 집합과 정확히
  일치하는지 확인한다. 시드나 sklearn 버전이 바뀌어도 분할이 흔들리지 않는다.
- 제외 컬럼: `material`(전 실험 상수), `Z_CurrentFeedback` / `Z_DCBusVoltage` /
  `Z_OutputCurrent` / `Z_OutputVoltage`(EDA 001의 전역 상수 4개).
- 요약 방식: 채널별 `mean`/`std`/`min`/`max`, `Machining_Process` 단계 비중(`proc_frac_*`),
  `n_rows`, 그리고 가공 조건 `feedrate`/`clamp_pressure`.

### (2) 윈도우 크기 100행, 겹치지 않게(non-overlapping)
- **왜 100행인가.** 가장 짧은 실험(`No`=5, 23)이 462행이다. 100행이면 그 실험도 윈도우 4개를
  확보하므로 어떤 실험도 표본 1개짜리로 남지 않는다. 동시에 100행은 원본 샘플링 기준 약 10초
  구간이라 절삭 구간 하나의 통계를 내기에 충분히 길다. 윈도우를 더 짧게(예: 50행) 하면 표본은
  늘지만 창 안 통계의 분산이 커지고 같은 실험에서 나온 조각들끼리의 상관이 더 심해진다.
- **왜 겹치지 않게인가.** 겹치는 윈도우는 서로 절반 이상 같은 원시 행을 공유하므로 정보량은
  안 늘고 행 수만 부풀린다. 게다가 나중 단계에서 누군가 실수로 윈도우 단위 셔플 분할을 하면
  겹침은 곧바로 노골적인 누수가 된다. 표본을 "그럴듯하게" 늘리는 대신 정직한 253행을 택했다.
- **끝의 나머지(100행 미만)는 버린다.** 총 954행(전체 26,332행의 3.6%)이 버려졌다.
  마지막 짧은 윈도우를 남기면 (a) 그 윈도우만 표본 수가 적어 std/min/max가 더 노이지하고,
  (b) `n_rows`가 사실상 "이 실험의 마지막 윈도우인가"를 인코딩하는 라벨성 피처가 된다.

### (3) 라벨은 실험 단위 라벨을 윈도우로 broadcast
`train.csv`의 실험 단위 라벨을 `No` 기준 merge로 그 실험의 모든 윈도우에 그대로 복사했다.
**윈도우마다 다른 라벨이 생기는 것이 아니다.** `feedrate`/`clamp_pressure`도 같은 방식으로
실험 내 모든 윈도우에 동일하게 붙는다.

원본 라벨은 "가공 종료 후 공구 상태" 하나뿐이라, 실험 초반 윈도우에도 "worn" 라벨이 붙는다.
이건 이 데이터셋 구조상 불가피한 라벨 노이즈이며, 004가 003보다 나아지지 않는다면
**모델 문제가 아니라 이 broadcast 자체가 원인일 수 있다**는 점을 기억할 것.

### (4) 식별 컬럼 `No`, `window_idx`
모든 행에 `No`(원래 실험 번호)와 `window_idx`(그 실험 안에서 몇 번째 윈도우인지, 0부터)를 남겼다.
`No`는 그룹 분할·CV에 필수이고, `window_idx`는 시간 순서 확인/디버깅용이다.
**둘 다 피처가 아니다 — 학습에서 반드시 제외할 것.**

### (5) 스케일러 파일은 만들지 않았다 (002와 다른 점)
002는 `features_v1_scaler.json`(train 전체로 fit)을 남겼지만, 003에서 확인했듯 CV에서는 그 파일을
쓰면 안 되고 폴드 안에서 다시 fit해야 한다. v2는 그룹 CV가 필수라 폴드 내부 재적합이 더더욱
필수이므로, 오용될 소지가 있는 전역 스케일러 파일을 아예 만들지 않았다. 저장된 CSV는 **원 스케일**이며,
스케일링이 필요하면 `Pipeline(StandardScaler, ...)`로 폴드 안에서 처리할 것.

## 트러블슈팅

- **`n_rows`가 상수가 되는 문제.** 002에서는 실행 길이(462~2,332)가 유의미한 피처였지만,
  고정 크기 윈도우에서는 항상 100이다. 별도 예외 처리를 넣지 않고 002에서 쓰던
  train 기준 zero-variance 필터가 자동으로 걷어내도록 뒀다 — 필터가 실제로 작동하는지를 확인하는
  덤도 됐다.
- **zero-variance 필터의 NaN 처리.** v1 코드의 `train_std[train_std.fillna(0.0) == 0.0]`은
  boolean mask는 fillna된 값으로 만들면서 인덱싱은 원본 Series에 하는 형태라 의도는 맞지만 읽기
  어렵다. v2에서는 `train_std.fillna(0.0)[train_std.fillna(0.0) == 0.0]`로 명시적으로 바꿨다.
  결과는 동일하다(이번 실행에서는 std가 NaN인 컬럼 자체가 없었다).
- **`Machining_Process` 값 정규화.** 002와 같이 `.str.strip().str.title()`을 적용해
  `"end"`/`"End"`를 합쳤다. 윈도우 안에 등장하지 않는 단계는 비중 NaN이 아니라 **0.0**으로 채운다
  (`fillna(0.0)`). 이걸 빼먹으면 짧은 윈도우마다 결측이 대량 발생한다.
- **행 수가 같은 실험 쌍이 눈에 띄어 중복을 다시 의심했다.**
  (5, 23)=462행, (7, 22)=565행, (8, 20)=605행, (2, 21)=1668행. `No`=8은 test, `No`=20은 train이라
  만약 동일 파일이면 즉시 누수다. MD5 해시로 25개 파일을 전부 재확인한 결과 **byte-identical 쌍은
  기존에 알려진 (14, 24), (19, 25) 둘뿐**이었다. 행 수 일치는 우연(또는 동일 가공 프로그램)이며
  누수가 아니다.
- **분할 재현성.** `train_test_split`을 다시 호출하지 않고 002 결과를 리터럴로 고정했다.
  sklearn 버전이 바뀌면 같은 seed라도 분할이 달라질 수 있는데, 그러면 003과의 비교가 무의미해진다.
- 실행 시간은 수 초 수준(21개 CSV, 253회 집계). 캐시는 두지 않았다.

### ⚠️ 반드시 지킬 것 — 그룹 누수 방지 (이번 실험에서 가장 중요)

같은 실험에서 나온 윈도우들은 **하나의 시계열을 자른 조각**이라 서로 독립이 아니다. 인접 윈도우는
같은 공구·같은 소재·같은 세팅에서 몇 초 차이로 기록된 값이며, `feedrate`/`clamp_pressure`/라벨은
아예 동일하다. 따라서:

1. **`train_test_split(..., shuffle=True)`, `KFold`, `StratifiedKFold`를 윈도우 행에 쓰지 말 것.**
   그렇게 하면 실험 11의 윈도우 12개가 train, 11개가 test에 들어가 사실상 답을 보여주는 셈이 된다.
   이 경우 balanced accuracy가 0.9+로 치솟을 수 있는데 **그건 성능이 아니라 누수다**
   (CLAUDE.md "고성능 = 누수 의심 먼저").
2. **그룹 컬럼은 `No`.** 교차검증은 `LeaveOneGroupOut(groups=No)` 또는
   `GroupKFold(n_splits=4, groups=No)`를 쓸 것. 003이 실험 단위 LOO를 했으므로, 직접 대응되는 것은
   **`LeaveOneGroupOut` (train 16개 실험 = 16폴드)**이다.
3. **train/test 실험 배정은 이미 파일에 반영돼 있다.** train 파일에는 `No` ∈ {1,2,3,5,6,7,9,10,11,
   13,17,18,20,21,22,23}만, test 파일에는 `No` ∈ {4,8,12,15,16}만 들어 있다. 두 파일을 합쳤다가
   다시 나누지 말 것.
4. **스케일링/피처 선택/오버샘플링은 전부 폴드 안에서.** 201행이라 SMOTE 등이 "가능해" 보이지만,
   그룹을 무시하고 합성 샘플을 만들면 held-out 실험과 거의 같은 윈도우가 학습 폴드에 생긴다.
   굳이 한다면 학습 폴드 내부에서만, 그리고 폴드 경계를 넘지 않게.
5. **지표는 윈도우 단위와 실험 단위 둘 다 보고할 것.** 윈도우 예측을 실험 단위로 집계
   (다수결 또는 평균 확률 임계)한 성능이 003과 직접 비교 가능한 수치다. 윈도우 단위 점수만 보고하면
   긴 실험이 과대 대표된다(`No`=11 혼자 23/201).

### 003과의 비교 기준

- **같은 지표를 쓸 것: F1 / balanced accuracy / ROC AUC.** 주 지표는 003과 동일하게
  **balanced accuracy**.
- **003의 기준선: LOO balanced accuracy 0.500(로지스틱) / 0.475(RF) — 사실상 우연 수준.**
  004가 개선이라고 말하려면 실험 단위로 집계한 balanced accuracy가 0.5를 **유의하게** 넘어야 한다.
- **라벨 셔플(permutation) 점검을 반드시 반복할 것.** 003은 셔플 귀무분포가
  0.406 ± 0.194였다. 004에서는 셔플도 **그룹을 유지한 채**(실험 단위로 라벨을 섞어서) 해야 한다 —
  윈도우별로 라벨을 섞으면 귀무분포 자체가 망가진다.
- **test 52행(실험 5개)은 마지막 확인용 1회.** 윈도우가 52개라도 독립 실험은 5개뿐이다.
  003의 경고("hold-out을 반복해서 들여다보지 말 것")가 그대로 유효하다.

### 이번 실험 결과가 나쁠 경우의 해석 순서
1. 그룹 누수 없이도 우연 수준이면 → 표본 수가 원인이 아니었다는 뜻. (3)번 "타겟 재검토"
   (003 다음 액션)로 넘어갈 것.
2. 윈도우 단위 점수는 높은데 실험 단위 집계 점수가 낮으면 → 모델이 "어느 실험인지"를 학습한 것.
   `M_sequence_number_*`, `proc_frac_*` 같은 진행 위치 피처를 빼고 재실험할 것.
3. 윈도우 크기를 바꿔 가며 점수를 짜내지 말 것 — 100/200/50을 다 돌려 제일 좋은 걸 고르면
   그건 16개 그룹짜리 CV에 대한 선택 편향이다. 크기를 바꾸려면 근거를 먼저 문서화할 것.
