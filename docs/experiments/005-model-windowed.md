# 005. 윈도우 단위 모델 학습·평가 (tool_condition, features_v2)

## 날짜
2026-09-04

## 한 일
`src/models/train_windowed.py`를 작성해 실행했다 (`python src/models/train_windowed.py`).
입력은 004가 만든 윈도우 단위 피처(`data/processed/features_v2_train.csv` 201행/실험 16개,
`features_v2_test.csv` 52행/실험 5개, 188열)이고, 타겟은 `tool_condition_worn`이다.
아래 수치는 전부 그 스크립트가 stdout에 출력한 JSON에서 그대로 가져왔다 — 하드코딩·추정 없음.
같은 수치를 `reports/metrics.json`의 `"005"` 키에 등록했다.

004의 "⚠️ 반드시 지킬 것 — 그룹 누수 방지"와 "003과의 비교 기준"을 그대로 따랐다. 003 대비
**바뀐 변수는 딱 하나 — 입력 피처 테이블의 집계 단위**다 (실험 1건=1행 → 실험 1건=윈도우 여러 행).
모델·하이퍼파라미터·지표는 003과 동일하게 고정했다.

### (1) 피처 정의와 누수 차단
피처 = 전체 188열 − {`No`, `window_idx`, `tool_condition_worn`, `passed_visual_inspection_yes`,
`machining_finalized_yes`} = **183개**. `load_split()`이 train/test 양쪽에 대해
`assert banned not in features`로 5개 컬럼이 피처 목록에 없음을 매 실행마다 확인한다
(004가 지시한 대로 `window_idx`를 003의 4개에 추가). train/test 피처 컬럼 순서 일치
(`assert features == test_features`)와 **train/test 실험 집합이 겹치지 않는지**
(`assert not set(g_train) & set(g_test)`)도 매 실행 확인한다. 실행 결과
`banned_columns_in_features = []`, `train_test_group_overlap = []`, 피처 결측 0건.

### (2) 교차검증: `LeaveOneGroupOut(groups=No)` — 16폴드
004가 지정한 대로 그룹 컬럼은 `No`. 폴드마다 **한 실험의 윈도우 전체(4~23개)**가 통째로 held-out
된다. 같은 실험의 윈도우는 하나의 시계열을 자른 조각이라 서로 독립이 아니므로
`KFold`/`StratifiedKFold`/행 단위 셔플 분할은 쓰지 않았다. 003의 실험 단위 LOO(16폴드)와
1:1로 대응된다.

- **스케일링은 폴드 안에서만.** `StandardScaler`를 Pipeline에 넣어 폴드마다 15개 실험으로만 fit.
  004는 오용을 막으려고 전역 스케일러 파일을 아예 만들지 않았고, 이 스크립트도 만들지 않는다.
- **윈도우 단위 지표**는 16폴드의 held-out 윈도우 예측 201개를 모아(pooled) 한 번에 계산.
- **실험 단위 지표**는 같은 예측을 실험별로 집계. 두 가지를 다 계산했다:
  - `mean_prob`: 그 실험 윈도우들의 예측 확률 평균에 0.5 임계 (평균 확률이 그대로 ROC 점수)
  - `majority_vote`: 윈도우 하드 예측의 다수결 (동점은 1, `mean >= 0.5`와 일관). 1로 투표한 비율이
    ROC 점수
  - **주 수치는 `mean_prob`의 balanced accuracy** — 003과 직접 비교할 값이다.
  - 왜 필요한가: 윈도우 단위 점수는 긴 실험에 끌려간다(`No`=11 혼자 23/201). 실험 단위 집계는
    실험마다 정확히 한 표를 준다.

### (3) 모델: 003과 동일, 탐색 없음
독립 그룹 수는 여전히 16개다(004: "행 수는 12배가 됐지만 독립적인 실험은 여전히 16개"). 그리드서치를
하면 16그룹짜리 CV 점수로 설정을 고르게 되어 그 점수가 정직한 추정치가 아니게 된다 — 003과 같은
이유로 **고정값**을 썼다.

- 주 모델: `LogisticRegression(penalty="l2", C=0.1, class_weight="balanced", max_iter=1000,
  solver="lbfgs")` + `StandardScaler` Pipeline. 결정론적이라 시드 반복 없음(std=0).
- 비교 모델: `RandomForestClassifier(n_estimators=200, max_depth=3, class_weight="balanced")`,
  **시드 5개(0~4)**로 반복해 평균±표준편차 보고.

### (4) 라벨 셔플(순열) 검정 — 그룹 유지
004의 경고대로 **실험 단위로** 라벨을 섞었다(`shuffle_labels_by_group()`): 실험별 라벨 16개를
실험들 사이에서 permute한 뒤 그 실험의 모든 윈도우에 broadcast. 윈도우별로 섞으면 각 실험 안에
양쪽 라벨이 섞여 들어가 귀무분포 자체가 망가진다. 로지스틱으로 10회(시드 0~9) 같은
`LeaveOneGroupOut`을 반복했다.

### (5) 진행 위치 피처 점검
004가 "`M_sequence_number_*`가 가공 진행 위치를 인코딩하므로 피처 중요도를 반드시 확인할 것"이라고
지시해서, 최종 RF(seed 0)의 상위 10개 중요도를 리포트에 함께 출력한다.

못했다. 003 대비 개선 없음.**

### 윈도우 단위 vs 실험 단위 — "실험 암기" 신호 점검

004가 경고한 "윈도우 단위 점수가 실험 단위 집계 점수보다 훨씬 높으면 실험을 통째로 암기한 것"
패턴을 CV와 hold-out 양쪽에서 확인했다.

- **CV(LeaveOneGroupOut)에서는 그 패턴이 없다.** 윈도우 0.381 vs 실험 0.438(로지스틱),
  윈도우 0.468 vs 실험 0.463/0.513(RF) — 오히려 윈도우 쪽이 같거나 낮다. 폴드마다 실험 전체를
  빼는 그룹 CV가 암기 경로를 실제로 차단하고 있다는 뜻이다(그리고 차단하고 나니 남는 신호가 없다).
- **hold-out RF에서는 그 패턴이 그대로 나타났다 — 숨기지 않고 적는다.**
  RF(seed 0) hold-out **윈도우 단위 balanced accuracy 0.735 / ROC AUC 0.837**인데
  **실험 단위 집계는 0.333(mean_prob) / 0.583(majority_vote)**이다. 원인은 test 5개 실험의
  윈도우 수 불균형이다: `No`=12(unworn, 22윈도우)와 `No`=15(worn, 13윈도우)가 52개 중 35개(67%)를
  차지해, 이 두 실험 안에서 윈도우를 잘 맞히면 윈도우 단위 점수가 크게 오른다. 반면 실험 단위로는
  `No`=12의 평균 확률이 0.502로 임계 바로 위에 걸려 틀린다.
  → **이 0.735/0.837은 성능으로 보고할 수 없는 수치다.** train/test는 실험 단위로 분리돼 있어
  (`train_test_group_overlap = []`) 학습-평가 간 누수는 아니지만, 긴 실험의 과대 대표로 부풀려진
  값이다. 004가 "윈도우 단위 점수만 보고하면 긴 실험이 과대 대표된다"고 경고한 바로 그 사례이며,
  이번 실험에서 실험 단위 집계를 주 지표로 고른 결정이 옳았음을 보여주는 반례로 기록한다.

의미도 제한적이다. 004의 "해석 순서" 2번(진행 위치 피처를 빼고 재실험)은 해당 조건(윈도우 高 / 실험
低가 CV에서 발생)이 성립하지 않으므로 **실행하지 않았다**.

### Hold-out sanity check (test 5개 실험 / 52윈도우 — 최종 성능 아님, 1회만 조회)

train 201윈도우 전체로 다시 학습한 모델을 test 실험 5개(`No` = 4, 8, 12, 15, 16)에 **딱 1회** 적용.

| 모델 | 수준 | accuracy | F1 | balanced accuracy | ROC AUC |
|---|---|---|---|---|---|
| LogisticRegression | 윈도우(52) | 0.404 | 0.537 | 0.416 | 0.471 |
| LogisticRegression | 실험(5, mean_prob) | 0.600 | 0.667 | 0.583 | 0.500 |
| RandomForest (seed 0) | 윈도우(52) | 0.731 | 0.750 | **0.735** | **0.837** |
| RandomForest (seed 0) | 실험(5, mean_prob) | 0.400 | 0.571 | 0.333 | 0.667 |
| RandomForest (seed 0) | 실험(5, majority_vote) | 0.600 | 0.667 | 0.583 | 0.833 |

실험별 평균 확률 (RF seed 0): `No`=4(true 0) 0.553, 8(true 1) 0.471, 12(true 0) 0.502,
15(true 1) 0.824, 16(true 1) 0.745.

**이 표는 "최종 성능"이 아니라 sanity check다.** 윈도우가 52개여도 독립 실험은 5개뿐이라 실험 1건이
실험 단위 accuracy를 20%p씩 흔든다. 003의 경고("hold-out을 반복해서 들여다보지 말 것")가 그대로
유효하며, 이번에 1회 썼다. 위 RF 윈도우 단위 0.735/0.837은 앞서 적은 대로 긴 실험 과대 대표의
산물이므로 **성능 근거로 인용하지 말 것.**

### 결론

1. **003 대비 개선 없음.** 실험 단위 집계 balanced accuracy가 003의 0.500(로지스틱)/0.475(RF)에서
   005의 0.438(로지스틱)/0.463~0.513(RF)로, 개선이라 부를 변화가 없다. 모든 값이 그룹 유지 셔플
   귀무분포(0.406 ± 0.177) 안에 들어간다.
2. **표본 수 가설은 기각.** 003의 "다음에 해볼 것 1번(표본 수를 늘린다)"을 004+005가 그대로
   실행했지만, 행을 16 → 201로 12배 늘려도 우연 수준 그대로다. 004가 미리 지적한 대로
   **독립 그룹 수는 여전히 16개**였고, 유효 표본은 행 수를 따라가지 않았다.
3. **누수는 없다.** 컬럼 assert, train/test 그룹 무중복 assert, 그룹 유지 셔플 검정을 모두 통과했다.
   문제는 "부풀려진 성능"이 아니라 "없는 신호"다.
4. **다음 의심 대상은 라벨/타겟이다.** 004가 미리 적은 대로, 실험 단위 라벨("가공 종료 후 공구
   상태")을 실험 초반 윈도우까지 broadcast하는 구조 자체가 라벨 노이즈원일 수 있다. 004의 "해석
   순서" 1번(표본 수가 원인이 아니었다 → 타겟 재검토)에 해당한다.

## 트러블슈팅

- **실험 단위 집계 방식을 하나로 정하기 어려웠다.** 004는 "다수결 또는 평균 확률 임계"라고 둘 다
  허용했다. 사후에 좋은 쪽을 고르면 그 자체가 선택 편향이므로, **둘 다 계산해서 둘 다 보고하고**
  주 수치는 미리 `mean_prob`(평균 확률 ≥ 0.5)로 못 박았다 — 평균 확률이 ROC AUC용 점수로도 그대로
  쓰여 임계값과 무관한 지표까지 한 번에 나오기 때문이다. 결과적으로 RF에서 majority_vote(0.513)가
  mean_prob(0.463)보다 높게 나왔지만, 이건 두 값 모두 귀무분포 안이라 유의한 차이가 아니다.
- **다수결 동점 처리.** 윈도우 수가 짝수인 실험(예: `No`=2의 16개)에서 8:8 동점이 가능하다.
  `vote_frac >= 0.5`로 동점을 1(worn)로 보내 `mean_prob >= 0.5`와 규칙을 일치시켰다. 임의 규칙이지만
  두 집계가 서로 다른 임계 관례를 쓰는 혼란보다는 낫다고 판단했다.
- **`lambda` late binding (003에서 이어짐).** RF 시드별 팩토리를 `lambda s=seed: make_rf(s)`로
  기본인자 바인딩했다. `lambda: make_rf(seed)`로 쓰면 5회 전부 마지막 시드로 돈다. 003의 트러블슈팅
  기록 덕에 처음부터 피했고, 시드별 값이 실제로 다른 것(0.489/0.498/0.430/0.474/0.449)으로 확인했다.
- **순열 검정에서 라벨을 어느 단위로 섞을지.** 첫 구현 충동은 003의 `rng.permutation(y)`를 그대로
  쓰는 것이었는데, 그러면 한 실험 안에 0과 1이 섞여 들어가 (a) "실험 단위 라벨" 구조가 깨지고
  (b) 실험 단위 집계 라벨이 정의되지 않는다. `shuffle_labels_by_group()`으로 실험 16개의 라벨을
  실험들 사이에서만 permute하도록 분리했고, `aggregate_to_experiments()`에
  `assert (per_exp["n_labels"] == 1).all()`을 넣어 한 실험이 두 라벨을 갖는 상황이 생기면 즉시
  터지게 했다.
- **hold-out 윈도우 점수 0.735가 나왔을 때.** CLAUDE.md "고성능 = 누수 의심 먼저"에 따라 먼저
  누수를 찾았다. `train_test_group_overlap = []`이라 실험 단위 분리는 확실했고, 원인은 누수가 아니라
  test 실험별 윈도우 수 불균형(`No`=12가 22개, `No`=15가 13개로 52개 중 35개)이었다. 수치를 지우지
  않고 원인과 함께 "인용 금지" 표시를 달아 남겼다.
- **ruff E501.** RF 5시드 LOGO를 한 줄 리스트 컴프리헨션으로 쓴 게 102자였다. `ruff format`이
  제안한 대로 줄바꿈했다.
- **윈도우 크기는 건드리지 않았다.** 004가 "윈도우 크기를 바꿔 가며 점수를 짜내지 말 것"이라고
  못박았으므로 100행 고정으로만 돌렸다. 결과가 나빠도 50/200을 시도하지 않았다.
- 전체 실행 시간은 1분 내외(LOGO 16폴드 × 모델 6종 + 순열 10회 × 16폴드). 캐시는 두지 않았다.

## 다음 액션 / 에이전트 지침

### 다시 시도하지 말 것
- **표본 수를 더 늘리는 방향(윈도우 세분화, 오버랩 윈도우, 증강)은 하지 말 것.** 005가 그 가설을
  실제로 검증했고 기각됐다. 행을 12배 늘려도 독립 그룹은 16개 그대로라 점수가 움직이지 않는다.
  오버랩 윈도우는 행 수만 부풀리고 누수 위험만 키운다(004 (2) 참고).
- **윈도우 크기(100)를 바꿔 가며 재시도하지 말 것.** 004의 지시가 그대로 유효하다. 50/200/300을
  다 돌려 제일 좋은 걸 고르면 16그룹 CV에 대한 선택 편향일 뿐이다.
- **`features_v2` 위에서 모델만 바꿔 성능을 짜내지 말 것.** 003과 같은 이유다. 선형/비선형 모두
  귀무분포 안이다. XGBoost/SVM으로 0.6이 나오면 그건 16그룹 CV의 분산이다.
- **16그룹 데이터로 하이퍼파라미터 탐색을 하지 말 것.**
- **hold-out 5개(`No` = 4, 8, 12, 15, 16)를 다시 들여다보지 말 것.** 003에서 1회, 005에서 1회
  썼다. 세 번째부터는 사실상 검증셋이 되어 hold-out으로서의 가치를 잃는다.
- **hold-out RF 윈도우 단위 0.735 / AUC 0.837을 성과로 인용하지 말 것.** 긴 실험 과대 대표의
  산물이며 같은 조건의 실험 단위 점수는 0.333이다.
