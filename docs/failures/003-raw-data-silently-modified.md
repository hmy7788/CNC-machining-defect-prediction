# 003. `data/raw/`의 원본 파일 2개가 세션 중 조용히 바뀌어 있었음

**태그**: `#data` `#process`

## 발견한 날짜
2026-09-04 (파이프라인 3단계 완료 후, 사용자 질문에 답하려고 `experiment_01.csv`를 다시 열어보다가 발견)

## 무엇을 발견했나
`experiment_01.csv`, `experiment_02.csv` 딱 2개 파일만 — 나머지 23개 실험 파일, `train.csv`,
`학습통합데이터`의 파일들은 전혀 안 바뀜 — 헤더/데이터의 구분자가 `,`(쉼표)에서 `, `(쉼표+공백)로
바뀌어 있었다. 이 상태에서 `pd.read_csv(path)`(skipinitialspace 없이)로 읽으면 첫 컬럼을 뺀 나머지
컬럼명 전부에 앞공백이 붙어 정확한 컬럼명 매칭이 깨진다 (`df["Machining_Process"]`가 `KeyError`).

## 원인 (확인됨)
**에이전트/스크립트 버그가 아니라 사용자가 가독성을 위해 두 파일을 직접 수동으로 정렬(align)한
것**이었다. 에이전트에게 미리 알리지 않고 진행해서, 에이전트 쪽에서는 원인을 알 수 없는 "조용한
변경"으로 보였다.

## 왜 기록해두는가
`data/raw/`는 git이 추적하지 않으므로(`.gitignore`), 이런 수동 변경이 있어도 `git status`로는
전혀 드러나지 않는다. CLAUDE.md의 "data/raw 절대 수정 금지"는 에이전트 대상 규칙이지만, 사람이
직접 편집할 때도 같은 이유로 위험하다: `data/raw/`를 다루는 스크립트들은 정확한 원본 포맷(쉼표
구분, 공백 없음)을 전제로 컬럼명을 매칭하기 때문에, 정렬을 위한 공백 추가만으로도 파이프라인이
깨진다.

## 조치
- 두 파일은 git 히스토리(`6db31cb` 커밋 시점)에서 원본(정렬 안 된) 버전으로 복구했다 — 이게
  스크립트가 기대하는 정확한 형태다.
- 복구 후 EDA·전처리·모델 스크립트 3개를 재실행해 이미 문서화된 수치가 전부 그대로 재현됨을
  확인했다 — `docs/experiments/001~003`의 결과는 이 일과 무관하게 유효하다.

## 에이전트 지침
- `data/raw/`에서 예상과 다른 파싱 에러(특히 정확한 컬럼명을 찾지 못하는 `KeyError`)가 나면,
  버그를 의심하기 전에 **사용자에게 그 파일을 최근에 직접 편집했는지부터 물어본다** — 이번처럼
  가장 흔한 원인이 스크립트 버그가 아니라 수동 편집이었다.
- 사용자에게: `data/raw/` 파일을 가독성 등의 이유로 직접 손대실 계획이면, 미리 알려주시면
  스크립트가 그 포맷도 견고하게 처리하도록(`skipinitialspace=True` 등) 미리 반영해둘 수 있습니다.
